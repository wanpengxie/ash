# 做一个普通人愿意用的 App

先回答「来这里办什么、第一眼看谁、下一步按哪里」。功能齐全和测试通过不能替代这三个答案。**设置页列对象，应用页讲发生的事；分组行只用于二级设置。**只改本次授权的界面和交互，不借设计增加业务能力。

## 怎么做

1. **先做应用地图，再做单屏**：先看产品任务、现有页面和最新接口，读 [TASTE.md](TASTE.md) 所指的共享口味。明确应用身份、主空间、核心对象、主要动作和手势，画清入口、标签、详情/抽屉、返回与跨应用落点；区分可用能力和规划。地图用法见 [应用地图](references/app-map.md)。沿用项目的令牌、图标和组件。缺的信息只有会改变方案才问，已有答案不再问。
2. **选参照**：找一个优秀的同类 App 的实际页面或官方图，写清借它哪一种信息组织或动作；不要只列品牌名。用 [屏型骨架](references/layouts.md) 开始，勿从零堆字段。
3. **说方向**：动手前一句话说明「这一屏以什么为主，如何组织，借鉴谁」。同时注明影响理解的假设、真实能力边界。多方案仅用于确有取舍的方向，不默认堆三套皮肤。
4. **做稿**：用 [组件规格](references/components.md) 组织真实中文内容。高保真稿以 360×800 dp 为基准，交付可编辑 HTML 和 PNG；HTML 的导航、选择、主操作要能演示本次路径。示例内容在交付说明中标明，不能假称线上事实。加载/空/失败保留相同骨架，只为关键状态补稿。
5. **看图复核**：渲染实际尺寸，按 [清单](references/review.md) 自查。再请任务指定的独立验证者读技能、打开 PNG；附每屏方向、参照、源文件、能力边界。返回 `done` 或 `needs_work`，后者必须指出具体屏幕、可见问题和用户影响。无独立验证者时如实标记待验证，不能自己代签。
6. **改与交付**：只改真实问题，重出受影响图并复验。给出每屏路径、验证结论、修改和仍未验证项。主人批准设计后才进入被授权的施工阶段；截图不能宣称 Android 或真机验收通过。

## 每屏硬规矩

- 首屏以日期、内容、当前事件或对象的整体画面作焦点；对象有身份，状态可看见。不要套「分组标题+白色圆角组+行+右箭头」做应用首页。至多一个实心主按钮，控件退后，不堆文字链。
- 中性色占绝大部分；品牌 accent 至多两处。真实好坏状态可用语义色，并同时写出状态，不能靠颜色猜。
- 正文对比度 ≥4.5:1；触控区至少 48×48dp。沿用字号令牌，不为塞内容缩字。时间、数量、状态不可省略；标题通常 ≤14 汉字，按钮 2–6 字，一段说明最多两行。
- 只用项目的单色线性图标，功能图标有无障碍名称。不用 emoji、渐变、大光晕、彩色左边框卡、每段一个图标、无意义数字、卡套卡、大段使用说明。
- 先呈现事情和结果，再呈现配置；只在用户需要时展开高级项。每个可见动作都对应已有能力；已记下、待做、在做、等你、完成要说真话。
- 固定底栏不盖内容；长列表能滚动。大字体重排、不裁字；深色沿用主题色，尊重安全区与系统返回。

不把低频边界做成新产品机制。常见失败用保留内容、一句实话和一个可继续的动作解决；需要业务改造的先指出边界。

## 好的样子

任务首页可用计数筛选、完成环、时间轨道和紧凑工作卡直接表达责任与日程，不强制套「大日期+一句小结」，不把首页写成散文；设备有整体连接画面与身份卡，设置收进更多。详情先讲进展或等待原因，再给来源与行动。提醒未安排时显示「已记下，提醒还没安排」和重试，不能叫添加失败。

## 常见错误

把应用画成设置页；把装饰进度和虚构活动当作「活的」；把接口字段铺满首屏；用很多小字链代替操作；借高级设置藏掉必要状态；编造正在做、已通知或已成功；只检查代码而没打开PNG。

## 怎么核对

按 references/review.md 看真实图、量尺寸和对比度，演示主路径，再由独立验证者给done/needs_work；交付区分设计通过、主人批准和真实应用验收。
