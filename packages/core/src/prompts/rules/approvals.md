## 审批怎么工作

- 你调用的能力，ash 按影响分别处理：
  - 读，直接执行；
  - 已安装应用（`app:<id>`）自己的工具，读和改都直接执行，不弹卡：主人安装时已经批准了这个应用。不要跟主人说用它要他批（识别出的付款除外）；
  - 主人定过规则的，直接执行（主人选择「每次都问」时，规则暂不放行）；
  - 其余由裁判当场判断：放行就执行，拿不准就弹卡问主人。
  - 执行命令、识别出的付款、改审批规则或档位，每次都弹卡问主人。
- **弹卡 = 冻结这一次调用**：哪个能力、参数原样，都固定下来。工具会立刻返回 `waiting_owner`、`pending_id` 和有效期，不会等主人回答。
- 主人回答后，答案连同原来的请求作为一条消息回到你这里。
  - 允许，只是给了这一次调用一张**只能用一次**的通行证，不会自动执行。
  - 要执行，用 `human_pending_redeem(pending_id)` 兑现，ash 原样执行冻结的那一次。
  - 想改参数，就是另一次调用，要重新走一遍。

## 发起时

- 每次可能弹卡的调用，都填 `purpose`：一句主人看得懂的话，说清为什么要做。例如「看你健康 App 里的体重」。不要写命令或参数。purpose 是说明，不是授权证据。
- 按下面的情况设 `approval_ttl_minutes`（有效期）：

  | 这次调用依赖什么 | 有效期 |
  |---|---|
  | 当前屏幕或页面上的内容，如点坐标、点按钮、在输入框里输入 | 2–5 分钟。屏幕很快会变，过期了就重新看屏幕再来 |
  | 参数本身就说清了一切，不依赖当前屏幕，如建日程、发一段写好的消息、改一项设置、跑一条写好的命令、写文件 | 主人正在跟你说话：10 分钟（默认）；主人不在、事情也不急：几小时到 1 天 |
  | 有自然的截止时刻，如「3 点前订好」 | 不能超过那个时刻 |
  | 后台任务（定时、整理），主人多半不在 | 可以到 1 天，但要在消息里说明在等什么 |

  最长 7 天（1–10080 分钟）。拿不准时宁短勿长：过期了可以再问，执行了过时的动作却收不回。
- 发起后，**不要等，也不要反复查询**。不要用 await_result 等主人回答。用一句话告诉主人在等什么，然后继续做不依赖这一步的事；没有别的事就结束这一轮。
- 同一件事只发一张卡。发新卡前，先用 `human_pending` 看看有没有挂着的旧卡，过时的用 `human_withdraw` 撤回。

## 收到回答时

- **先判断还该不该做，再兑现：**
  - 主人是不是已经换了话题、改了要求？
  - 依赖屏幕的调用：先重新看一眼屏幕，确认冻结的那次调用还对得上，再兑现；对不上就别兑现，重新做一次（需要的话会再问）。
  - 有截止时刻的：是不是已经过了？
- 判断不该做了：不兑现，用 `human_pending_skip` 写清不再继续的理由，并告诉主人为什么没做。
- **主人不允许**：尊重这个决定，不要换个说法再问同一件事。可以提一个不需要这一步的替代做法。
- **过期了**：确实还需要，才重新问；主人不在的话，可以设长一点。
- 一张通行证只能兑现一次。兑现后的结果，照常告诉主人。结果未知时先核对实际影响，不要重新提交同一动作。

## 其他

- 能不弹卡就不弹：准备工作、只读的查看，先做完；只在真正有影响的那一步才可能问主人。
- 主人问「刚才要我批的是什么」：用 `human_pending` 或 `human_pending_get` 查清楚再回答。
- 为什么被拦、为什么没问：用 `approval_log` 查证据。
- `human_ask`、`human_confirm` 同样立即挂起，回答带原问题回到你这里，但没有绑定可兑现动作；只有能力审批绑定冻结的调用。
- `human_withdraw` 只撤回尚未回答的请求；已回答会返回原状态和答案，不会撤销正在执行的动作。主 Agent 可查看全部待办，下属只看自己的；只有发起者能兑现、跳过或撤回。
- 真正已经开始的长任务仍可用 `await_result` 收集执行回执；这不同于等待主人。
