# AR6 effect-to-ledger detector foundation

## Current production scenario (2026-10-02)

`packages/core/test/arch/effect-scenario.test.ts` now starts the production Core with a fresh SQLite ledger and a separately running fake Android host. The fake host independently records a real `/call` and `/present`; a read of the actual `USER.md` bytes witnesses the managed-file effect; a live router subscriber observes `gate.passed` before the host receives the gated call. The test then compares those four observations with persisted request, event, and terminal-response messages using the detector below. Removing the actual delivery or gate event from the persisted trace makes the check fail. The host's queued response, notification channel, and file hash/version are independently specified or computed, not copied from ledger replies. The synthetic host and owner are not a physical Android device or an independent human review; AR6's device-side final sign-off remains separate.

Reproduce: `node --expose-internals --import tsx --test packages/core/test/arch/effect-scenario.test.ts`.

`packages/core/test/arch/effect-audit.ts` is a pure checker for four separately observed effect classes: device calls, notifications, intrinsic file writes, and gate releases. It requires nonempty ledger and independently observed effects supplied in chronological order, all four effect classes by default, unique effect-to-message attribution, exact target/word/body and (where observed) result equality, and a unique later response with the request's reverse sender/recipient and same word. An intrinsic write requires `self.changed` between request and response with matching path and caller; if the response supplies a version, the event version must match. The append, apply-plan, and rollback contracts do not return a version, so their path/caller/time match remains explicitly **unverified**, not a false pass or a claim that a valid write failed. A gate release must identify an existing request; the independently observed gate release must precede that request's actual device-call effect, though the request may already be in the ledger. This checks only explicitly observed protected calls, not every device call (including owner-direct calls). A notification must be recorded as notification delivery, not merely queued or held.

Nine executable fixture tests include a valid four-effect trace with request→gate→response ledger order and gate→device external-effect order, plus deliberate omissions, wrong arguments/target/result, forged response identity and word, duplicate attribution/response, unrelated or late file-change events, missing version marked unverified, false notification outcome, forged/late/unassociated gate events, direct device call without gate, and ledger reordering. These fixtures validate the detector only. The `self.changed` correlation is limited to available path/caller/version/time fields; it is not a cryptographic causal proof or a substitute for runtime atomicity. The production scenario above adds live evidence beyond these fixtures but does not substitute for a physical-device regression or non-author review.
