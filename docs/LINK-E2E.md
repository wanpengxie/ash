# 中枢 ↔ 设备端到端加密（`ash-link/2`）

中转站（Cloudflare Worker，`ash-gw/1`）只起连接节点的作用，和 Tailscale 的 DERP 中继一样：它转发的是它读不懂、也改不了的数据，不提供任何内容。本文写威胁模型、握手、密钥和背书、配对，以及出错时说什么。

标注：**[核实]** 是查过代码或跑过的事实；**[推测]** 是没验证的判断。

## 1. 威胁模型

### 防什么

| # | 攻击者（中转站被攻破、被调取，或 Cloudflare 本身） | 怎么防 |
|---|---|---|
| 1 | 读内容：命令、文件、Codex 会话 | 中枢和设备之间跑 TLS 1.3，中转站只见密文 |
| 2 | 篡改、注入、重放、调换顺序 | TLS 记录层的 AEAD 和隐式序号：改一个字节、重放一帧、调换顺序，解密都会失败，连接断开，命令不会执行 |
| 3 | 冒充中枢 | 设备只认被它钉住的主人公钥签过背书的中枢连接密钥 |
| 4 | 冒充设备 | 中枢只认登记过的设备公钥（TLS 客户端证书） |
| 5 | 配对时掉包公钥（任一方） | 配对用一次性秘密 `k`（只在聊天和终端里出现，从不经过中转站）给双方的公钥做 MAC |
| 6 | 伪造关闭码，让设备以为自己被撤销或版本太旧而永久停下 | 关闭码在 TLS 里面发（`!close`），设备只信加密通道里的关闭码；外层关闭一律当网络断开处理，过一会儿重连 |
| 7 | 某台设备的密钥日后泄漏，解密以前录下的流量 | TLS 1.3 每次连接都用临时 ECDHE 密钥，有前向保密 |
| 8 | 换掉或抢占中转站后冒充任一方 | 信任不在中转站：设备钉的是主人公钥，中枢认的是登记的设备公钥，换中转站也绕不过去 |

### 不防什么（如实写明）

- **元数据**：谁和谁连、什么时候连、流量多大，中转站仍然看得到（DERP 也是这样）。
- **掐断服务**：中转站可以不转发、断开连接、乱发外层关闭码，结果只是连不上，两边会自动重连。中转站层面的撤销（`ash-gw/1` 外层连接收到 4003）仍会让设备记下「被撤销」，这是中转站协议本身的行为，本次不改中转站；被这样误伤的设备重新配对即可。
- **中枢或设备本机被攻破**：本文只管两者之间的线路。
- **主人公钥本身**：它留在 Android Keystore 里，只能签名，不在本文范围。

## 2. 分层

```
  ash-link/2 帧（challenge / hello / welcome / call / …，和 /1 一样，换了协议名）
  ── 按行分隔的 JSON（每行一帧，`!` 开头的是本层的控制行）
  TLS 1.3，双向证书认证（node:tls）
  ── 每条隧道消息是一段 TLS 字节，base64 文本
  中转站隧道（ash-gw/1 的 tun/ws.msg，原样转发）
```

**[核实]** Node 自带的 `node:tls` 可以跑在任意 Duplex 上：中枢用 `new tls.TLSSocket(duplex, { isServer: true, requestCert: true })`，设备用 `tls.connect({ socket: duplex })`。原型在一条消息管道上跑通了 TLS 1.3 双向认证（`TLS_AES_256_GCM_SHA384`）。中枢在手机上本来就用 Node 的 `fetch` 走 HTTPS 连中转站，所以手机上的 Node 带 TLS。

**[核实]** 中转站隧道（`DeviceStream`）有序、可靠，单条消息最大 4 MiB，二进制消息在中枢一侧会被当成 UTF-8 解码弄坏（`socketOf` 里的 `TextDecoder`），所以 TLS 字节按 base64 文本发。

为什么不用 Noise：Node 没有内置实现，要加一个依赖；而 TLS 1.3 现成、维护最多，加密、完整性、防重放、前向保密、换密钥全在里面。

本地回环（手机自己的 hand、手机自己的网页，`via: local`）不加密：它只在 127.0.0.1 上，凭本机令牌和签名进来，不经过中转站。规则在 `packages/core/src/edges/link-server/index.ts`：
- 经中转站进来的连接只能由 `acceptGateway` 交进来，而 `acceptGateway` 只接受已经完成 TLS 和背书校验的连接（带对端证书公钥）；
- 握手时 `hello.hand.public_key` 必须等于 TLS 对端证书的公钥。

## 3. 密钥和背书

| 密钥 | 在哪 | 用途 |
|---|---|---|
| 主人密钥（ECDSA P-256） | Android Keystore，不可导出 | 签中枢背书；签中转站上的授权（原样） |
| 中枢连接密钥（ECDSA P-256） | 中枢状态（`link_gateway` 表），PKCS#8 | TLS 服务端证书 |
| 设备密钥（ECDSA P-256） | 电脑 `~/.ash-device/state/device.jwk`（0600） | TLS 客户端证书；中转站登录；链接握手签名 |

证书是自签的，没有 CA，**只按公钥判断**（像 SSH 认主机密钥）：TLS 两侧都关掉证书链校验（`rejectUnauthorized: false`），握手完成后、发任何应用数据之前，各自取出对端证书里的公钥和期望值比对（SPKI DER 逐字节）。证书本身用一个最小的 DER 模板生成（`packages/link/src/cert.ts`，只有编码，没有密码学），签名用 `node:crypto`。

**中枢背书**（照 tailnet lock）：主人密钥签下面这段文本（和 `ash-gw/1` 一样，按行拼接，不是 JSON）：

```
ash-link/2
hub-key
<owner_key: SPKI base64url>
<hub_key: SPKI base64url>
<expires_at: 毫秒>
```

有效 30 天，剩不到 7 天时中枢在下一次开隧道前请 Keystore 重签。签名是 DER 或 r‖s（Keystore 给 DER），验签两种都接受。

## 4. 握手时序（经中转站）

```
中枢（TLS 服务端）                       中转站                     设备（TLS 客户端）
  开隧道 tun/ws.open /link  ─────────────────────────────────────▶
  版本通告（明文）{"t":"challenge","kernel":{"protocol":"ash-link/2"},…}  ─▶
                                                                     旧设备（/1）：协议不对，自己以 4008 关闭，不再重连
                                                                     新设备：开始 TLS
  ◀──────────────────────── ClientHello … Finished（TLS 1.3，双向证书）
  核对：设备证书公钥 = 登记的公钥                                       核对：（暂不信任，等背书）
  ── !hub {owner_key, hub_key, expires_at, sig, pair_mac?} ─────────▶
                                                                     核对：hub_key = 中枢证书公钥；
                                                                           owner_key = 钉住的主人公钥（首次连接用 pair_mac 证明）；
                                                                           sig 由 owner_key 签；未过期
  ◀──────────────────────────────────────── !device {pair_mac?}
  核对 pair_mac（首次连接）
  ── 以下全是 ash-link/2 帧，在 TLS 里 ──
  challenge ────────────────────────────────────────────────────────▶
  ◀──────────────────────────────────────────────────────── hello（签 nonce）
  welcome ──────────────────────────────────────────────────────────▶
```

- 明文的版本通告只是一个开关：新设备收到 `ash-link/2` 就开始 TLS，里面的 nonce 不用；收到别的协议名**不会**停下（那可能是中转站伪造的），只断开重连。旧设备照它原来的逻辑以 4008 关闭，中枢记一条「handshake.4008」。
- **[核实]** 旧设备收到 4008 后进程退出，但服务（launchd `KeepAlive`、systemd `Restart=always`）会把它再拉起来，于是反复 4008。它连不上，`device_update` 也就发不过去：只能在那台电脑上手动 `ash-device update --version-to … --sha256 …` 再重启服务。这是 `/1` 到 `/2` 的一次性代价（不做迁移）；`/2` 以后的版本不合可以在 TLS 里带可信的 4008。
- 握手计时（20 秒）从中枢发出版本通告时开始。设备那边的链接客户端可能先要了连接、等很久隧道才来，那段时间不计。
- 双方都只在核对通过后才把连接交给链接层，所以没通过核对的一方读不到也发不出任何链接帧。
- 本层控制行：`!hub`、`!device`、`!close {code, reason}`。链接帧总是以 `{` 开头。
- 关闭：一方带码关闭时先在 TLS 里发 `!close`，再关隧道。对端只采用 TLS 里的关闭码；没有 `!close` 就断了，按 1006（网络断开）处理并重连。
- 每行最长是一帧的上限（4 MiB）加一点余量，超了按 4400 关闭。

## 5. 配对（防掉包）

**[核实]** `ash-gw/1` 的配对请求只带 `ticket`、`pubkey`、`name`，主人公钥由中转站转交，所以中转站能在配对时掉包任一方的公钥。中转站本身不改，所以证明放在第一次加密连接里做。

1. `pair_start`（只有 `computer`、`server` 两类）：中枢向中转站要一个配对码（中转站只见它的哈希），再生成 32 字节的一次性秘密 `k`。返回**完整的安装命令**：

   ```
   curl -fsSL https://github.com/wanpengxie/ash/releases/download/device-v<版本>/install.sh | sh -s -- '<中转站>' '<配对码>' '<k>'
   ```

   脚本从 GitHub 发布页下载，安装包按发布页的 `SHA256SUMS` 校验。`k` 只出现在聊天和终端里，从不发给中转站。不再有中转站下发的配对页（`/p/<码>`）。
2. 设备 `ash-device setup --gateway … --pair <码> --secret <k>`：照旧向中转站提交配对请求、等批准，把 `k` 和中转站报来的主人公钥（还不可信）写进 `paired.json`。
3. Ash 批准（`pair_approve`）：中枢登记设备公钥，把 `k` 存在 `link_gateway` 表里（`pair_secret:<设备号>`），直到这台设备证明自己。
4. 第一次加密连接：
   - 中枢在 `!hub` 里带 `pair_mac = HMAC-SHA256(k, "ash-link/2\npair-hub\n<owner_key>\n<hub_key>\n<device_key>")`；
   - 设备核对通过，才钉住这个 `owner_key`（覆盖中转站报来的那个），删掉 `k`，回 `!device {pair_mac = HMAC(k, "…pair-device\n…")}`；
   - 中枢核对通过，删掉 `k`。之后的连接只靠钉住的公钥和背书。
5. 掉包会怎样：
   - 中转站掉包了**主人公钥**：设备在第 4 步算不出对的 `pair_mac`，断开，日志写明「中枢没能证明配对秘密，中转站可能掉包了主人公钥」，安装命令也会报这个错。
   - 中转站掉包了**设备公钥**：中枢登记的是假公钥。真设备连不上（证书公钥对不上，4001）；拿着假公钥的一方算不出设备的 `pair_mac`，中枢就撤销这条登记，配对变成 `failed`，原因写「设备没能证明配对秘密，中转站可能掉包了设备公钥；请重新配对」。

已经配对过的设备（没有 `k`）不受影响：它钉着的主人公钥就是当初配对时的那个（当时没有防掉包，等于首次使用即信任）。升级后照常连接。

## 6. 失败时说什么

| 在哪 | 情况 | 结果 |
|---|---|---|
| 中枢 | 设备证书公钥不是登记的 | 关闭 4001，`refused` 事件写「the device's key is not the one that was paired」，`diagnose` 显示 `handshake.4001` |
| 中枢 | 首次连接设备的 `pair_mac` 不对或缺失 | 关闭 4001，撤销这条登记，配对 `failed`，原因如上 |
| 中枢 | 设备讲旧协议 | 设备自己以 4008 关闭；`diagnose` 显示 `handshake.4008` |
| 设备 | 中枢证书公钥和背书不一致、背书不是钉住的主人签的、背书过期 | 断开，日志写具体哪一条，退避后重连（真中枢可能稍后才来） |
| 设备 | 首次连接 `pair_mac` 不对 | 断开，日志如上；`setup` 报错 |
| 两边 | TLS 记录被篡改、重放、乱序 | TLS 报错，连接断开，重连；没有命令执行 |

## 7. 本次一并去掉的：经中转站的网页

主人 10-15 定：不再有离开设备的纯网页端。所以：
- 中枢不再接受中转站转来的浏览器请求（HTTP 和 WebSocket，一律拒绝）；
- 不再有 `web_ui` 授权，配对不再有 `browser` 一类；
- 中转站发给中枢的权限只剩 `expose_capability`；
- 中转站本身不改：它的网页隧道和配对页没人用了，是死代码。

## 8. 下一步

- **设备上的本地前端**：电脑上的 Ash 程序在 127.0.0.1 提供网页，数据走这台设备已有的加密连接（链接的 human 通道）。网页代码随设备程序一起发布、一起校验，中转站不提供任何内容。
- **局域网直连**：两边在同一网络时直连，中转站只做兜底，减少掐断服务的影响。
- **中枢连接密钥轮换**：现在一直用同一把，背书 30 天续签；以后可以连密钥一起换。
